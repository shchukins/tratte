# Tratte

Персональный сервис, который читает электронные чеки из Gmail, сохраняет покупки в
PostgreSQL и показывает статистику через Telegram-бота. Целевая среда — домашний
сервер с Docker Compose. Gmail используется только с областью
`gmail.readonly`: сервис не меняет ярлыки, не перемещает и не удаляет письма.

## Что реализовано

- Первичный импорт за период и повторная синхронизация без дублей.
- Поиск по конфигурируемому ярлыку `чеки` и списку отправителей. Запрос не зависит
  от Inbox: архивированные письма с ярлыком обрабатываются. Корзина источником не
  используется.
- Парсеры «Билайн ОФД», «Первый ОФД», «Магнит ОФД» и осторожный общий HTML-парсер
  для других структурированных чеков, включая узнавание сетей «Пятёрочка»,
  «ВкусВилл» и «Магнит» по продавцу.
- Единая модель чека, товарных строк и фискальных реквизитов.
- Дедупликация по `ФН + ФД + ФПД`, затем по Gmail message ID.
- Нормализация названий, верхнеуровневые категории и ручные алиасы.
- Команды Telegram `/start`, `/help`, `/today`, `/week`, `/month`, `/top`,
  `/stores`, `/prices`, `/last`, `/sync`; доступ ограничен allowlist.
- Отдельные процессы API, бота и планировщика; история запусков синхронизации.
- HTML писем не сохраняется. OAuth-токен хранится в БД в зашифрованном виде.
- Миграции Alembic, обезличенные фикстуры, модульные и интеграционный тесты.

## Архитектура

```text
Gmail API (read-only, label:чеки)
            │
            ▼
 parser registry → normalization → PostgreSQL
                                   ├─ Telegram bot
                                   └─ FastAPI /health
```

В Docker Compose PostgreSQL доступен только внутренней сети. Данные лежат в
именованном томе `tratte_postgres_data`; контейнер можно пересоздавать без потери
БД. API по умолчанию публикуется только на loopback домашнего сервера.

## Предположения и ограничения

- Сервис персональный и обслуживает один Gmail-аккаунт. Таблицы допускают развитие
  в мультипользовательский вариант, но привязка данных к нескольким владельцам в
  MVP не реализована.
- Правило Gmail уже назначает всем нужным письмам ярлык `чеки`. Статус прочтения и
  нахождение в архиве значения не имеют.
- Известны отправители `ofdreceipt@beeline.ru`, `echeck@1-ofd.ru` и
  `info@ofd-magnit.ru`. Список можно изменить через `GMAIL_SENDERS` либо оставить
  переменную пустой, чтобы искать все письма с ярлыком.
- Парсеры проверены read-only на одном реальном свежем письме каждого из трёх ОФД
  31.08.2026: для всех извлеклись позиции, итог, дата, место, способ оплаты и полный
  фискальный ключ. Реальные письма и реквизиты в репозиторий не сохранялись;
  тестовые фикстуры повторяют только структуру и полностью обезличены. Изменение
  шаблона письма со стороны ОФД всё ещё может потребовать адаптации. Неизвестный
  формат получает статус `failed` и не останавливает синхронизацию.
- Автоматическая нормализация намеренно консервативна: разные вкусы и варианты не
  объединяются. Будущую LLM-классификацию можно подключить вместо/после
  `ProductNormalizer`.
- Telegram использует long polling, поэтому входящий порт для бота не нужен.
- Для домашнего сервера необходимы резервные копии Docker-тома; автоматический
  backup в MVP не включён.

## Запуск на домашнем сервере

Требуются Docker Engine и Docker Compose v2.

```bash
cp .env.example .env
python3 -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Запишите выданный ключ в `TOKEN_ENCRYPTION_KEY`, задайте сильный
`POSTGRES_PASSWORD`, токен Telegram и разрешённый user ID. Затем:

```bash
docker compose build
docker compose run --rm migrate
docker compose up -d api bot scheduler
docker compose ps
curl http://127.0.0.1:8000/health
```

На Linux ограничьте чтение конфигурации: `chmod 600 .env client_secret.json`.

Первичный импорт и ручная синхронизация:

```bash
docker compose run --rm api app import-receipts --since 2026-08-01
docker compose run --rm api app sync
docker compose run --rm api app retry-failed
```

Повторный разбор конкретного письма и ручной алиас товара:

```bash
docker compose run --rm api app reprocess GMAIL_MESSAGE_ID
docker compose run --rm api app set-alias 'исходное название' 'нормализованное название' 'напитки'
```

### Резервное копирование PostgreSQL

Создать логический дамп (пароль берётся сервисом `db` из `.env`):

```bash
docker compose exec -T db pg_dump -U tratte -d tratte -Fc > tratte-backup.dump
```

Файл дампа храните вне системного диска сервера. Восстановление проверяйте на
отдельной тестовой БД; не выполняйте его поверх рабочей БД без свежей копии.

## Google OAuth

1. В [Google Cloud Console](https://console.cloud.google.com/) создайте проект.
2. Включите Gmail API, настройте OAuth consent screen и добавьте свой Google-аккаунт
   как test user, если приложение остаётся в режиме Testing.
3. Создайте OAuth Client ID типа **Desktop app** и скачайте JSON как
   `client_secret.json`. Не коммитьте этот файл.
   На Linux-сервере файл должен читаться только непривилегированным UID
   приложения из Docker-образа:

```bash
chown 10001:10001 client_secret.json
chmod 600 client_secret.json
```

4. На компьютере с браузером проще выполнить локальную установку и `app gmail-auth`.
   Для авторизации непосредственно на домашнем сервере запустите:

```bash
docker compose --profile setup run --rm --service-ports gmail-auth
```

Команда напечатает ссылку. Если сервер удалённый, сначала создайте SSH-туннель
`ssh -L 8080:127.0.0.1:8080 user@home-server`, затем откройте ссылку локально.
Redirect URI должен завершиться на `http://localhost:8080/`. После согласия
refresh token шифруется ключом `TOKEN_ENCRYPTION_KEY` и сохраняется в PostgreSQL.

Если внешний OAuth consent screen остаётся в статусе **Testing**, Google выдаёт
refresh token со сроком жизни 7 дней для Gmail scopes. Для постоянной серверной
работы переведите приложение в **In production** и выполните `gmail-auth` ещё раз.
Публикация может потребовать публичные ссылки на домашнюю страницу и политику
конфиденциальности приложения.

Важно: не меняйте `TOKEN_ENCRYPTION_KEY` без переноса/повторной авторизации — иначе
существующий OAuth-токен расшифровать будет невозможно.

## Telegram BotFather

1. Откройте `@BotFather`, выполните `/newbot`, задайте имя и username.
2. Поместите выданный токен в `TELEGRAM_BOT_TOKEN`.
3. Узнайте свой числовой Telegram user ID и запишите его в
   `TELEGRAM_ALLOWED_USER_IDS`. Несколько ID разделяются запятыми.
4. Перезапустите процесс: `docker compose restart bot`.

Не публикуйте bot token и не добавляйте `0`/пустой allowlist как способ открыть
бота всем пользователям.

## Локальная разработка и проверка

```bash
python3.12 -m venv .venv
. .venv/bin/activate
pip install -e '.[dev]'
alembic upgrade head
pytest
ruff check .
app serve
```

Структура проекта:

```text
app/
  parsers/       интерфейс и реализации HTML-парсеров
  services/      Gmail, импорт, нормализация, статистика, отчёты, secrets
  bot.py         Telegram-команды и allowlist
  cli.py         команды запуска и обслуживания
  models.py      SQLAlchemy-модели
migrations/      Alembic
tests/fixtures/  только обезличенные HTML-чеки
docker-compose.yml
```

## Добавление нового формата ОФД

Прочитайте одно письмо локально, удалите email, адрес, ИНН, ФН/ФД/ФПД, Gmail ID и
другие персональные/фискальные значения, сохранив DOM-структуру. Добавьте только
обезличенную фикстуру и специализированный parser перед `GenericReceiptParser` в
реестре. Перед публикацией выполните проверки из [SECURITY.md](SECURITY.md).
