## Вопрос и результат

Почему между двумя полными месяцами изменились расходы: уплаченная цена,
количество или состав покупок? На вымышленных данных августа–сентября 2026
расходы выросли с 850 до 1 410 ₽. Проверяемое бухгалтерское тождество:

**850 + 100 (цена) + 420 (количество) + 70 (вход) − 30 (выход) = 1 410 ₽.**

Несопоставимые строки, сверка и округление имеют отдельные нулевые вклады,
а не исчезают из моста. Охват сопоставления: 800/850 ₽ и 1 320/1 410 ₽.
Молоко даёт +380 ₽ (150 цены + 230 количества), рис +140 ₽ (−50 + 190).
Каждый товар раскрывается до восьми наблюдений. В июле есть чек без итога:
полный мост недоступен (`insufficient_data`), неизвестное не заменяется нулём.

Это synthetic пример, не вывод о реальных расходах, инфляции или экономии.
Уплаченная цена может включать выбор магазина и акции. Gmail не гарантирует
полноту всех покупок. Масса, объём и штуки не складываются в общее количество.

## Путь от источника до результата

Gmail → parser → PostgreSQL → подтверждённый mapping → SQL → immutable BI snapshot
→ Superset. Публичное demo использует отдельный генератор с seed 20261027;
личные письма и рабочая БД для воспроизведения не нужны.

Scope периодов/магазина/категории задаётся до расчёта. Выбранная версия mapping
проверяется в одной REPEATABLE READ READ ONLY транзакции с SQL. Superset читает
снимок с явным snapshot_id, as_of, версией mapping и хешами методики/SQL;
фильтр товара в detail не меняет рассчитанные итоги всей корзины.

## Единая воспроизводимая приёмка

Полная инструкция создания **нового одноразового PostgreSQL 16**:
[demo/README.md](demo/README.md). Затем из корня проекта:

```bash
TRATTE_DEMO_DATABASE_URL='postgresql+psycopg://postgres:synthetic-demo@localhost:55437/demo' \
  python -m analytics.demo.postgres
```

Команда отказывает при непустой БД. Она применяет все миграции, загружает
вымышленные чеки и явно подтверждённый synthetic mapping, вызывает production SQL,
сравнивает результат с независимыми ручными [ожиданиями](demo/expected.json),
проверяет неполный июль, публикует snapshot и повторно проверяет сохранённый документ.
Результат: `output/demo/report.json` и `output/demo/superset.zip`, привязанный
к опубликованному snapshot. Импорт ZIP в Superset — отдельный шаг по инструкции #6.

CI запускает Ruff, всю pytest suite на PostgreSQL, затем эту команду в отдельной
пустой `public_demo` БД. Ошибка любого шага блокирует promotion в `deploy`.
Oracle отвергает отсутствующие, повторные и неизвестные компоненты моста,
сверяет их сумму с полным отклонением и проверяет статус доступности результата.
Проверки не зависят от личной БД или секретов внешних сервисов.
