# ADR-001: отдельный подтверждаемый слой сопоставления

Дата: 2026-10-25. Статус: принято как проектное решение #2; DDL/миграции — #3.

## Контекст

Сейчас ReceiptItem хранит original_name/normalized_name, quantity/unit,
unit_price/total/category. ProductAlias меняет normalized_name/category существующих
строк. Нет стабильного product_id, размера упаковки и истории mapping.
Название с одинаковым текстом не гарантирует идентичность; quantity для весового
товара уже может быть в кг. Предварительный аудит даёт только 8 повторных кандидатов
для августа–сентября; массовая нормализация не нужна для первого результата.

Существующие Superset datasets пропускают unknown операции через ELSE total.
Поэтому новый контракт нельзя получить только косметическим обновлением графиков.
Нужна отдельная версия аналитических datasets; существующие отчёты сохраняются до
явной проверки изменения их семантики.

## Решение

В #3 добавить отдельные таблицы, не менять поля/семантику ReceiptItem и ProductAlias:

1. `analytics_products`: стабильный ID, каноническое описание конкретного
   варианта (бренд/тип/вкус/жирность/упаковка), comparison_unit (kg/l/piece).
   Разные упаковки по умолчанию — разные варианты. Family ID и сравнение вариантов
   между собой отложены; смена упаковки не называется shrinkflation автоматически.
2. `analytics_mapping_versions`: ID версии, версия правил, created_at. Утверждённая
   версия неизменна; исправление создаёт следующую. Расчёт выбирает версию явно.
3. `analytics_item_mappings`: составной PK `(mapping_version_id, item_id)`, FK на
   продукт, status (`confirmed/rejected/unresolved`), источник/примечание,
   `quantity_basis` (`source_weight/source_volume/package_count/piece_count`),
   коэффициент перевода source quantity в comparison unit. Неподтверждённый mapping
   не имеет действующего коэффициента. CHECK коэффициента > 0, совместимость
   размерности и FK обязательны.

Для package_count коэффициент задаёт содержимое одной упаковки в kg/l; сохранить
явно content_quantity/content_unit для проверки. Для source_weight/source_volume
использовать только преобразование исходной единицы — не умножать на упаковку.
Масса не преобразуется в объём. Для piece_count сравнивать один подтверждённый
вариант с известной семантикой штуки.

Это минимальная additive-схема без каталогов брендов/магазинов, fuzzy matching и
нового frontend. Mapping на уровне item_id позволяет не переносить ошибочное
соответствие на все одинаковые имена. CLI предлагает кандидатов по точному имени
и свойствам, но применяет только явное подтверждение. Новые item_id остаются
unresolved до следующей версии. При reprocess удалённые item_id не переносятся
автоматически: CLI выдаёт stale/missing mappings; пересчёт старой версии блокируется
при изменившихся/исчезнувших строках. В #3 нужно сохранять fingerprint используемых
полей строки в mapping и проверять его; политика FK/delete уточняется миграцией.

Версия mapping сама по себе не восстанавливает изменённые исходные данные.
Immutable observations/полный ledger не входят в MVP; до них старый расчёт после
изменения источника маркируется stale, а не молча воспроизводится как прежний.

## Что оставить в SQL и Superset

SQL #4: grains чеков/строк, timezone, операции, сверка, coverage и качества.
SQL #5: агрегация по продукту/периоду, взвешенная цена и точное разложение факторов.
Начать с обычных запросов/views; materialized views, ETL scheduler и отдельный
API нужны только при измеренной необходимости. SQL и методика лежат в репозитории.
Superset #6 отображает рассчитанные метрики; обязательных изменений бота/импорта нет.

## Альтернативы

- Только normalized_name в virtual dataset: подходит для разведки, но не для
  подтверждённого эффекта цены; нет упаковки и проверяемой идентичности.
- Огромный CASE в каждом графике: дублирует правила, затрудняет исправления и
  согласованность. Один общий SQL-слой воспроизводимее.
- Встроить product_id прямо в importer: усиливает связь аналитики с приёмом чеков
  и требует разрешить неоднозначности до импорта. Для MVP не требуется.
- ML/LLM/entity resolution: не нужен для восьми стартовых кандидатов. Результат #1
  не разрешает автономные объединения.

## Последствия и MVP

Первый результат охватывает подтверждённые повторные варианты двух полных месяцев.
Остальные расходы остаются видимыми как остаток с причиной. Сначала SQL-витрины,
затем дашборд на проверенных bar/table/line; waterfall и drill проверяются в UI #6.
Публичный кейс использует synthetic источник. PostgreSQL schema/service deployment,
коммит/push и публикация кейса — отдельные действия после этой локальной реализации.
