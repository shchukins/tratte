# Подтверждаемый каталог — issue #3

Контракт `analytical_identity_v1`, реализация ADR-001. Каталог изолирован от
ReceiptItem/ProductAlias и импорта. Новая строка без mapping остаётся unmatched;
никакие имена, категории, суммы и единицы источника не переписываются.

## Схема и семантика

- `analytics_products`: стабильный строковый ID **конкретного физического варианта**,
  comparison_unit (`kg/l/piece`), неизменяемая JSON specification с описанием,
  брендом, отличительными свойствами, упаковкой и content_quantity/content_unit.
  Разные вкусы/жирность/размеры получают разные ID. Неизвестное не угадывается.
- `analytics_mapping_versions`: ID = SHA256 канонического полного review, версия
  правил, дата применения и manifest. Manifest содержит выбранный scope, parent
  и точный набор item_id, решений и спецификаций. Порядок списков и десятичная
  запись размера упаковки нормализуются перед хешированием.
- `analytics_item_mappings`: PK `(mapping_version_id, item_id)`, отдельный nullable
  FK `source_item_id → receipt_items.id ON DELETE SET NULL`, fingerprint источника,
  FK продукта, status, source, note, quantity_basis и factor Numeric(18,9).
  Historical item_id сохраняется после reprocess; FK не мешает удалению источника.
  Неподтверждённые строки не имеют product_id, basis или factor.

`confirmed` — явное решение проверяющего по конкретному item_id. `unresolved` —
решения пока нет; `rejected` — предложенное соответствие отменено/отклонено.
Последние два статуса исключены из сопоставимых количеств. Отсутствующие в выбранной
версии item_id считаются unmatched; новая загрузка сама не расширяет каталог.
Статусы и происхождение относятся к mapping, а не к изменяемому глобальному SKU.

`package_count`: quantity — число купленных упаковок; factor — содержимое одной
в kg/l. Например, 2 × 930 ml = 1,86 l, 2 × 1 l = 2 l, с разными product_id.
`source_weight/source_volume`: quantity уже измерено в исходной единице;
factor = 0,001 для g/ml, 1 для kg/l. Размер упаковки не умножается ещё раз.
`piece_count`: одна подтверждённая штука конкретного варианта, factor = 1.
Масса, объём и штуки не преобразуются друг в друга. Неизвестное содержимое нельзя
подтвердить как package_count; явно известную штуку можно учитывать в piece.
В CLI принимаются русские единицы источника и kg/g/l/ml/piece; точные алиасы
перечислены в `UNITS`. Кандидаты намеренно сохраняют популяцию audit-v1 (шт/кг).
Граммы/литры можно выбрать явно через export, без расширения исходных восьми ключей.

## Применение и ручная проверка

Сначала миграция **в разрешённой среде**, через обычный CI → deploy для сервера:

```bash
.venv/bin/python -m alembic upgrade head
mkdir -p .local-evaluations/analytical-identity
.venv/bin/python -m app.cli analytics candidates 2026-08-01 2026-09-01 \
  .local-evaluations/analytical-identity/candidates.json
```

Выборка использует два соседних завершённых календарных месяца Europe/Moscow,
parsed RUB ПРИХОД, положительные суммы/количества/цены и минимум два разных чека
в каждом месяце. Совпадение точного normalized_name и audit_unit — лишь кандидат.
Original_name каждой строки доступно для проверки. Параметры scope/состав review
нужно сохранять; свежий candidates отражает текущую БД, не исторический срез аудита.

```bash
# Список из candidates либо явно выбранные item_id; никаких решений по одному имени.
selected_ids=$(jq -r '[.[].items[].item_id] | unique | map(tostring) | join(",")' \
  .local-evaluations/analytical-identity/candidates.json)
.venv/bin/python -m app.cli analytics export .local-evaluations/analytical-identity/review.json \
  "$selected_ids" '2026-08+2026-09:repeated-2-receipts'
```

Export не пишет в БД. Review содержит evidence (исходное/нормализованное название,
quantity/unit) и fingerprint каждого item_id; сначала всё unresolved. Сверьте
свойства всех строк, затем добавьте products и измените решения выбранных строк.
Не редактируйте evidence/fingerprint: apply сверяет оба с текущим источником.
Fingerprint также учитывает цены/суммы/категорию, дату покупки, операцию, валюту,
статус, магазин и timestamps чека. Изменение алиаса тоже делает версию stale.

Пример **синтетического** элемента products:

```json
{
  "id": "synthetic-milk-plain-930ml",
  "description": "Synthetic milk 930 ml",
  "brand": "Synthetic brand",
  "variant": "plain 2.5%",
  "packaging": "bottle 930 ml",
  "comparison_unit": "l",
  "content_quantity": "930",
  "content_unit": "ml"
}
```

В соответствующем decision задайте `status: confirmed`, этот `product_id`,
`quantity_basis: package_count`, source (кто/на каком основании подтвердил)
и note с основанием. Для весового перца — отдельный product с comparison_unit kg,
null content_quantity/content_unit и `quantity_basis: source_weight`.
Для unresolved/rejected product_id и basis должны быть null. Products содержит
ровно варианты, на которые ссылаются confirmed решения. Бренд/вкус/тип упаковки,
которых нет в источнике, не достраиваются; при сомнении оставляйте unresolved.
Не приравнивайте разные упаковки и не называйте их смену shrinkflation.

```bash
# Явное применение проверенного файла = подтверждение всех записанных решений.
version=$(.venv/bin/python -m app.cli analytics apply .local-evaluations/analytical-identity/review.json)
.venv/bin/python -m app.cli analytics validate "$version"
```

Apply атомарен: сначала проверяет весь набор, затем сохраняет каталог и mapping
одной транзакцией. Повтор того же review возвращает тот же ID, без новых строк.
Неизвестные/повторные ID, конфликт спецификации существующего product_id,
несовместимые размерности и устаревшие источники отклоняются. Не меняйте базовые
таблицы SQL вручную: совместимость размерностей проверяется сервисом, CHECK/FK
дополняют её в БД. Параллельные конфликтующие применения могут завершиться
ошибкой уникальности без частичного результата; повторите после завершения первого.

## Исправление, расширение и backfill

```bash
.venv/bin/python -m app.cli analytics revise "$version" \
  .local-evaluations/analytical-identity/review-next.json --add-item-ids 101,102
```

Без `--add-item-ids` команда копирует прежние решения для исправления. С параметром
добавляет только явно выбранные новые строки как unresolved. Измените ошибочное
решение на rejected, очистите product_id/basis и укажите причину. Если продукт
больше не используется ни одним confirmed решением, удалите его из products
данного review. Изменение спецификации требует **нового product_id**. Затем apply
создаёт новую версию с parent; старые решения не переписываются.

Backfill — применение конкретного сохранённого review к его точному набору ID.
Для той же БД и неизменённых источников он идемпотентен. Не переносите item_id между
независимыми БД. После исправления источника export нового выбранного набора
нужен заново: revise старой stale-версии блокируется. После reprocess новые ID
не наследуют mapping даже при совпадении имён.

Версии и продукты защищены от UPDATE/DELETE триггерами PostgreSQL/SQLite.
Исключение — обнуление live FK после удаления исходной строки. Перед **каждым**
расчётом/выдачей производного результата потребитель обязан вызвать
`validate_version(session, version)` в той же согласованной транзакции чтения.
Функция сверяет manifest/каталог/строки mapping/fingerprint и отклоняет stale,
missing и повреждённые данные. Чтение сырых таблиц без этой проверки не является
поддерживаемым расчётом. У SQLite приложение включает foreign_keys для всех
своих соединений; внешние SQLite-клиенты должны включать PRAGMA сами.

Версия не восстанавливает старый ReceiptItem и не является полным ledger.
Ключ будущего расчёта/кеша включает mapping_version, версию методики, scope,
периоды и дату среза. Выбор новой версии требует нового расчёта; автоматических
материализованных результатов/кешей в #3 нет. Старую версию можно выбрать явно
для проверки прежнего решения, пока источник не stale. Никакого неявного latest.

## Приватность и откат

Review, evidence, канонические названия и результаты candidates — приватные данные.
CLI создаёт файлы 0600 и отказывается перезаписывать существующие. Храните их вне
Git; `.local-evaluations/` исключён. Не публикуйте файлы или сырые ошибки с вводом.
В открытом репозитории остаются только синтетические примеры и тесты.

Миграция `0003_analytical_identity` только добавляет три таблицы, индекс, CHECK/FK
и триггеры. Исходные таблицы не меняются, backfill автоматически не запускается.
Перед серверным применением создайте существующий PostgreSQL backup по README.
Откат после остановки потребителей аналитики:

```bash
.venv/bin/python -m alembic downgrade 0002_weekly_summary_deliveries
```

Он удаляет **весь аналитический каталог и версии**, сохраняя исходные чеки,
ProductAlias и weekly deliveries. Сначала сохраните приватный backup или review,
если каталог нужен; восстановление review возможно только на неизменённом источнике.
Откат ошибочного mapping выполняется новой версией, без downgrade схемы.

## Проверка готовности

Синтетические тесты покрывают 930 ml/1 l, g/kg, ml/l, неизвестную упаковку,
весовую строку без повторного умножения, разные варианты, отмену решения,
идемпотентность, выбранный scope, stale источники, delete/reprocess, CLI/0600,
неизменность БД и upgrade → downgrade → upgrade на SQLite и PostgreSQL.
PostgreSQL-тест использует отдельную временную схему в одноразовой тестовой БД
`TRATTE_AUDIT_TEST_DSN`; никогда не указывайте production DSN.

Код и синтетические проверки не доказывают подтверждённое реальное покрытие.
Стартовый scope аудита — 8 ключей, 90 строк (43/47). Его ручное подтверждение,
применённая версия в целевой БД, CI и проверенная серверная доставка фиксируются
отдельно. До этих шагов #3 нельзя закрывать как полностью принятое.
