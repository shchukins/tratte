# expense_comparison_audit_v1

Статус: контракт аудита #2. Расчёт факторов и UI реализуются в #4–#6.

## Источник и периоды

Единственный источник — сохранённые электронные чеки одного Gmail-аккаунта.
Отсутствие наблюдения не доказывает отсутствие покупки; полнота личных расходов
неизвестна. Это не индекс официальной инфляции.

Timezone: `Europe/Moscow`. Периоды — два соседних завершённых календарных месяца,
вычисленных по локальной дате покупки. Интервалы полуоткрытые `[начало, конец)`:
для выбранной пары `[2026-08-01 00:00+03, 2026-09-01 00:00+03)` и
`[2026-09-01 00:00+03, 2026-10-01 00:00+03)`. Октябрь в срезе 25.10 неполный.

`as_of` имеет обязательный UTC offset; receipts.created_at <= as_of, дата покупки
< as_of. Пропущенные/будущие даты показываются в overview, но не распределяются
по месяцам. В JSON месяцы — локальные даты первого числа; точные timestamps — UTC.

## Операции и валюты

Классификация после trim и lower, только точные значения:

| Исходное значение | Класс | Роль в MVP |
| --- | --- | --- |
| `ПРИХОД` | purchase | Допустим для сопоставления при валидных значениях |
| `ВОЗВРАТ ПРИХОДА` | purchase_return | Отдельно, вне price/quantity comparison |
| null / пустое | unknown | Отдельно, не выводить тип по знаку суммы |
| Всё остальное | other | Отдельно, до разбора семантики источника |

MVP сравнения — RUB; остальные валюты не конвертируются и не суммируются между
собой. Денежные reason-группы разделены по валюте. Общие счётчики операций/единиц
не являются денежными итогами. Аудит monthly_receipts показывает **записанные**
суммы по валютам и типам; это не net cash flow. Знак возврата автоматически не
меняется. Валидная подтверждённая покупка имеет receipt.total > 0, item.total > 0,
quantity > 0, unit_price > 0. Нулевые/отрицательные/неполные значения диагностируются
отдельно и не получают выдуманных цен.

## Grains и сверка

- Receipt KPI: одна строка на receipt_id. Сумма/число/средний чек считаются до JOIN
  со строками. `COUNT(DISTINCT receipt_id)` не исправляет размноженную сумму.
- Item KPI: одна строка на item_id. Суммы категорий — из receipt_items.total.
- На чек: `receipt.total - SUM(item.total)`. Поле `mismatched_receipts` считает
  абсолютное отклонение > 0,01 ₽; точная и абсолютная суммы отклонений сохраняются
  отдельно. Отсутствие строк/null не приравнивается к нулевому отклонению.
- Повторяющиеся строки внутри чека лишь кандидаты на проверку: две одинаковые
  покупки могут быть легитимны. Автоматической дедупликации нет. Фискальная/Gmail
  уникальность уже обеспечивается уникальными ограничениями модели.

Цена из чека и `unit_price*quantity` проверяются с допуском 0,01 ₽. Сумма строки
остаётся источником затрат при скидках/округлении; арифметическое расхождение
показывается, а не исправляется. Будущая фактическая сопоставимая цена =
SUM(total)/SUM(comparable_quantity), не среднее/медиана unit_price.

## Кандидатное и подтверждённое покрытие

До #3 нет подтверждённого product_id и структурированной упаковки. Кандидатный
ключ аудита — **точное** normalized_name + audit_unit. Шт/шт./шт. или ед. группируются
только для поиска кандидатов, кг — отдельно. Они не подтверждают ни идентичность,
ни физическое содержимое упаковки. Прочие/null units — unsupported; граммы/литры
будут поддержаны после явных правил #3. Исходные имена нигде не возвращаются.

После просмотра частоты, но до расчёта эффектов, зафиксирован минимум **два разных
чека на ключ в каждом месяце**. Несколько строк одного чека дают одно наблюдение
для порога, но полную сумму затрат. Это минимальный продуктовый фильтр единичных
покупок, не доказательство статистической значимости и не защита от всех акций.
В срезе осталось 8 кандидатов; это позволяет начать с небольшого ручного каталога.

| Поле JSON | Определение |
| --- | --- |
| positive_rub_item_amount = A | Сумма положительных RUB-строк parsed чеков месяца, независимо от операции |
| eligible_purchase_item_amount = B | Из A только purchase и receipt.total > 0; ещё до отбора качества quantity/unit/identity |
| repeated_name_candidate_amount | Валидные строки ключей, встретившихся в обоих месяцах хотя бы в одном чеке |
| repeated_candidate_amount = C | Валидные строки ключей с минимум двумя чеками в обоих месяцах |
| candidate_coverage_of_positive_rub | C/A, месяц считается отдельно |
| candidate_coverage_of_eligible_purchases | C/B, месяц считается отдельно |
| confirmed_comparable_amount = D | В #2 всегда 0: каталог ещё не подтверждён |
| confirmed_coverage_* | D/A и D/B; при нулевом знаменателе null, не 0% |

A — наблюдаемый положительный оборот строк, **не все личные расходы**. B сохраняет
невалидные quantity/unit строки в знаменателе: их исключение не должно улучшать
видимость качества. Не усреднять два месячных процента и не подменять ими долю
всей истории. Суммы reason-групп могут включать отрицательные значения, а A —
только положительные RUB: сверять распределения в одинаковом scope.

## Причины несопоставимости

У каждой строки выбранной пары ровно одна основная причина в таком порядке:

1. `operation_unknown`, `operation_purchase_return` или `operation_other`;
2. `currency_not_rub`;
3. `invalid_receipt_total`;
4. `invalid_item_values`;
5. `missing_name`;
6. `unsupported_unit`;
7. `not_observed_in_both_periods`;
8. `too_few_receipts`;
9. `identity_unverified` — кандидат прошёл порог, но требует подтверждения.

Это взаимоисключающая воронка, а не полный перечень всех проблем строки.
Дополнительные ошибки показаны независимыми диагностическими счётчиками.
Отсутствие в другом месяце не означает прекращение выпуска/продаж товара.

## Статусы и представление результата

- `descriptive_only`: доступны записанные суммы/частоты и качество данных;
- `insufficient_data`: нет ни одного подтверждённого сопоставимого ключа с двумя
  чеками в обоих периодах или отсутствуют знаменатели/нужные наблюдения;
- `available_partial`: после #3 есть такой ключ; цена/количество объясняются только
  для подтверждённой части с двумя месячными coverage. Остальное явно отдельно.

Для среза #2: descriptive_only для сумм; insufficient_data для price/quantity.
Это семантический контракт будущих витрин, не реализованный API со статусами.
Порога для объявления «вся корзина объяснена» нет: нулевой residual нельзя получить
исключением неизвестного. Мост #5 обязан сходиться с выбранным итогом, включая
новые/исчезнувшие позиции, несопоставимую часть и сверку строк/чеков.

Медианная цена и число наблюдений допустимы как описательный график. Ни медиана,
ни наблюдаемое изменение цены не доказывают постоянное подорожание: влияют акции,
магазин, сорт и размер упаковки. «Корзина по прежним ценам» — сценарная стоимость
наблюдаемой части, не обещанная экономия.

## Свежесть и версии

Публикуются дата среза, последняя дата покупки, последний completed sync, состояние
последнего запуска и число failed за сутки. Это наблюдения, не гарантия полноты:
sync может завершиться без новых покупок, а ошибка до создания SyncRun не попадёт
в журнал. Новые импорты и исправления могут изменить прошлые месяцы.

В #3 mapping имеет версию; в #4–#5 фиксируются версия методики, mapping, пара
месяцев, scope фильтров и дата расчёта. Магазинный фильтр должен применяться **до**
вычисления P/Q, порога и состава сопоставимых ключей. Нельзя фильтровать готовые
общие факторы и называть их пересчётом для магазина.
